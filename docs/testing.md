# Testing Invariants

- `delay_seconds=0` in all tests — never add sleep. A job/task without a `retry` block gets the default 3 × 30s; the autouse fixture `no_retry_sleep` (`tests/conftest.py`) skips the sleep and fails the test (df-t242)
- Tests always use `tmp_path` for `db_url` (never a real path)
- `run_task` is thread-safe: each call creates its own SQLAlchemy `Session`
- No log files: a task's output is the `execucoes.output` column (`dataforge execucoes logs <id>`). The old line here named `execucao_{id}_{job}_{task}.log` files, which nothing writes (df-ahua.16.2).
- Real API on a socket: `tests/live_api.py` `serve_api()` runs `dataforge.api:app` under uvicorn in a thread on a free port (set `DATAFORGE_HOME` first) and stops it in a `finally`. Use it to follow an SSE stream (httpx's ASGITransport and Starlette's TestClient only return a response once it is finished) and for GUI tests, whose QNetworkAccessManager needs a socket. Its `add_gated_job`/`release_gated_job` give a one-task job the test ends when it wants, so a run is seen in progress. While the server runs, pump Qt with `processEvents()` plus a short `time.sleep`, not `QTest.qWait`: qWait keeps the GIL while it waits, so the server only answers between waits (2 s per request instead of milliseconds).
- GUI against the real API (df-ahua.16.4): `tests/test_gui_live_api.py`, one test per panel family, driven by the panels' own signals. Each one checks the contract of `tests/gui_contract.py`: `FieldReads.install` wraps the GUI modules' `json.loads` results and records every key the GUI looks up and whether the server sent it; `unsatisfied()` must be empty (lookups on one line are alternatives: one found satisfies the line). This is what catches a server/GUI drift such as df-ahua.16.1 (the run detail read a task `output` the stream never sent; the hand-written payloads of the other tests had it). A GUI test that feeds a handler a payload by hand tests rendering only; a new field the GUI reads needs a live test that reads it.
- There is no coverage gate (an earlier 80% claim was wrong). Coverage is measured per module with the test loop.
- Every CI job installs with `uv sync --frozen` from `uv.lock` (setup-uv, cached). The `tests` job measures branch coverage through `sys.monitoring` (`COVERAGE_CORE=sysmon`, Python 3.14+): on 3.12's C tracer coverage cost ~44% of the job (df-n8ac). The main ruleset requires the CI checks but not a PR up to date with main (df-0ha4: with that rule, each merge sent every other open PR back for a rebase and a full CI round). Two PRs that are each green can therefore break only together: the CI run of the push to main is what shows it, so read it after a merge. Auto-merge is on (`gh pr merge --auto --merge`).
- CI (`.github/workflows/ci.yml`) splits the engine suite (`tests/*.py` without `integration`) across shards: `tests-shard (k/2)` on Linux and `tests-windows-shard (k/3)` on Windows, each split by test duration (`pytest-split`) and run across the runner's cores (`pytest-xdist -n auto`); job `tests-gui` runs the GUI tests in their own process (df-t5cg). The required checks `tests` and `tests-windows` are gate jobs: they pass only when every part passed. Job `coverage` merges the parts' coverage into the `coverage.xml` the `sonar` job reads (sonar needs only it, not `orders`: df-n8ac.37; `tests` gates it), and `coverage` and `tests-windows` merge the shards' durations (`scripts/ci_durations.py`) into the actions cache the next run splits by (df-n8ac.13). Every shard of a run shuffles with the same seed, the run id, because the split depends on order; a rerun keeps it. More tests: raise the shard count in `ci.yml`. Locally the same: `pytest -n auto` (and `--splits N --group k` to reproduce one shard). Every test gets its own `DATAFORGE_HOME` (autouse `isolated_dataforge_home` in `tests/conftest.py`), so nothing reaches the real global database or another worker's; a module that needs one home for all its tests overrides that fixture by name. The GetFinance pipeline tests are not here: they live in the workspace, `workspaces/GetFinance/tests/` (fake values), and run in their own process with the workspace's `pytest.ini` (`pytest workspaces/GetFinance -m 'not integration'`; CI job `tests-getfinance`, whose coverage of `workspaces/GetFinance/scripts/` joins the same `coverage.xml`, and job `tests-getfinance-windows`, the same tests on Windows without coverage, gated by `tests-windows`: df-yivq). Their `integration` tests read the real data, read-only, through `GETFINANCE_DATA` and skip without it (df-bsb2.2.2). Until df-bsb2.2.7, the private GetFinance-Workspace repo keeps its own copy of these tests and its own CI.
- CI job `tests-windows` (`windows-latest`, Python 3.14 like every job and prod) runs the same engine suite (`tests/*.py` without `integration`, no GUI, no coverage) on native Windows, because production runs there (df-ahua.24); it also gates `tests-getfinance-windows`, the GetFinance tests on Windows (df-yivq). It is a separate job, not a matrix of `tests`, so the required check `tests` keeps its name. It sets `PYTHONIOENCODING=utf-8` for stdio only and deliberately not `PYTHONUTF8`: `open()` without `encoding=` keeps the cp1252 default production has, so a missing `encoding="utf-8"` fails there instead of hiding.
- Writing a test that must hold on Windows: write fixtures as bytes (`write_bytes(text.encode("utf-8"))`) or with `encoding="utf-8", newline=""` when the test compares bytes or hashes; `write_text` alone writes CRLF and cp1252 on Windows. A test that cannot exist on Windows (a file name NTFS cannot hold: `\`, `:`, a trailing dot or space, a newline) gets `@pytest.mark.skipif(sys.platform == "win32", reason="<why it cannot exist there>")`; if only the setup is impossible, skip the setup and keep the assertion. A real Windows bug in product code gets a bead and `@pytest.mark.xfail(sys.platform == "win32", reason="df-xxxx: ...", strict=True)`, never a skip.
- Deploy path guards have a Windows-only smoke, `scripts/smoke_deploy_windows.py` (CI job `windows-smoke`, `windows-latest`; df-llmm). It runs `dataforge.deploy.service` build/apply/rollback on NTFS and checks that nothing lands outside the target, in the ledger, or prunes `.env`/`data/`/ignored files/active triggers. Linux tests can't stand in: NTFS drops a trailing dot or space, reads `:` as a stream and ignores case (the code before PR #12 failed 19 of its 36 checks). Locally from WSL: Windows venv with pyproject's runtime deps minus PySide6, `PYTHONPATH=<repo>`, run through a `.cmd` with `cmd.exe /c` (`bd memories windows-smoke-recipe`).
- The same job then installs a release like prod, which has no C compiler (df-mvls): `scripts/prod/update-prod.ps1` into a fresh venv, as `deploy.sh` runs it, with a pip config that refuses every source build except PyYAML's (pure Python, `PYYAML_FORCE_LIBYAML=0`). A dependency with no wheel for prod's Python fails there, not at the deploy; a pure-Python one joins the `no-binary` line of that step in `ci.yml`.
- Qt objects must die on the GUI (main) thread. CPython's cyclic GC runs in whichever thread crosses the allocation threshold, so a collection on the uvicorn daemon thread or a `TestClient` portal thread used to free widgets left over by GUI tests off the GUI thread and segfault, at once or later in a `processEvents()` (df-3yh). `tests/conftest.py` therefore keeps the automatic collector off for the whole session and collects at each test's teardown on the main thread; the desktop app does the same with `dataforge/gui/gc_guard.py`. Do not call `gc.enable()` in a test, and do not call `gc.collect()` from a worker thread. GUI tests run with `QT_QPA_PLATFORM=offscreen`: `tests/conftest.py` sets it (setdefault) before Qt is imported (df-m4tz).
- Tests run in random order (`pytest-randomly`, in the `dev` group of `uv.lock`; df-ahua.8). Each run shuffles the modules and the tests inside them and prints `Using --randomly-seed=N` in the header (not under `-q`). It also reseeds `random` before each test from that seed. A failure that depends on order reproduces with the same command plus `--randomly-seed=N`; `-p no:randomly` turns the shuffle off. An order-dependent failure is a real finding: fix the leak (module state, env var, leftover file) or file a bead with the seed and the test (`-l erro:instavel`). The test loop passes `-p no:randomly` (`testloop.toml` `pytest_args`), so `map`, `mutate` and `check` always use the file order; `check` adds the Hypothesis profile `deterministic` (derandomize: each property's examples come from the test itself, not from `random`). Every other run loads the profile `no-deadline` (`dataforge/testing.py`, the pytest plugin that `tests/conftest.py` and each workspace's `tests/conftest.py` load, with the shared fixtures `db_url`, `dataforge_home` and `global_engine`; df-xkhx.7): the profile Hypothesis picked on its own (`default` locally, random with the example database; `ci` when it detects CI, derandomized without a database) minus the 200 ms per-example deadline, so a property on a slow disk fails on its rule, never on time. A `--hypothesis-profile` on the command line still wins; `pytest -v` prints the active one in the header.
- CI job `orders (k/2)` (every PR and push, in parallel; df-n8ac.14): the engine suite and the GetFinance suite (`workspaces/GetFinance`, its own pytest process; df-xkhx.1) in two more random orders, seeds `run id + k` in the run summary (one line per suite). The GetFinance step runs even when the engine one failed. `tests-getfinance` itself runs with seed `run id`. Both steps also pass `--hypothesis-profile=explore --hypothesis-seed=<seed>` (df-91aq): every other CI run starts from Hypothesis's own `ci` profile, which is derandomized, so a property tries the same examples on every PR; `explore` (`dataforge/testing.py`: not derandomized, no example database, blob printed) draws new ones from the seed. A property that fails there fails `orders`, which gates the merge like every job: the counterexample is a real bug or a wrong property, and becomes a bead with the seed. Reproduce with the same pytest command plus `--hypothesis-profile=explore --hypothesis-seed=<seed>`; `tests/test_testing_plugin.py` checks that the profile changes with the seed and repeats with it. It replaces the weekly `flaky-hunt`; the workflow has no schedule any more (dependency upgrades are Dependabot PRs).
- Coverage of a change, locally before a PR: `.venv/bin/python scripts/testloop/cli.py diff-cover` runs the engine tests with branch coverage of `dataforge/` (as the `tests` job does) and, in a pytest process of its own, the tests of each workspace that has a `pytest.ini` (today `workspaces/GetFinance`) with branch coverage of its `scripts/` (as `tests-getfinance` does; df-xkhx.3), and lists changed lines and branches no test runs, against `origin/main` (`--compare-branch REF` for another base; committed, staged and unstaged edits count). Exit 0 all covered, 1 something uncovered, 2 the tests failed. Not in CI: SonarQube Cloud judges new-code coverage on the PR (df-ahua.7). Files outside `dataforge/` and the workspaces' `scripts/` are not measured.
- **A leaked connection or file fails the run** (df-n8ac.19, df-g4z7): the shared plugin
  `dataforge/testing.py` turns `ResourceWarning` and `PytestUnraisableExceptionWarning` into errors
  for both suites, and collects garbage when each test module ends. The test that fails is the one
  running when Python noticed, often not the one that opened the object: at the latest the last
  test of its module. It is not a flaky test. The run's summary prints the command that shows where
  each object was opened (`PYTHONTRACEMALLOC=20 pytest -p no:randomly -W always::ResourceWarning
  -W always::pytest.PytestUnraisableExceptionWarning`; slow, so one module at a time). Remember that
  `-m 'not integration'` skips the real-data tests: run those files too when you touch what they cover.

## Test loop (find holes in a module's tests)

Design and first-slice results: `docs/adr/0004-automated-test-system.md`.

- Installed by `uv sync` (the `dev` group); run from the repo root; Linux or WSL only (`mutate` uses `os.killpg`).
- `tests/test_testloop.py` (the CLI) is marked integration and takes about 15 minutes; `-m 'not integration'` skips it. The eval harness tests moved to `tests/test_testloop_evals.py`, gitignored with `scripts/testloop/evals/`.
- `testloop.toml` (repo root) holds the per-repo settings: paths, test command, declared dependencies.
- A target's `copy` globs name files `mutate` copies beside the module and its tests. `mutate` runs mutmut, which runs the tests from `<copy>/mutants/` and brings there only the source dir (the module's top-level dir) and mutmut's defaults (`tests/`, `test/`, `pyproject.toml`, `setup.cfg`, the locks, `test*.py`); so each top-level entry of the copy that holds a `copy` file outside those goes in mutmut's `also_copy` (`.gitignore`, `dataforge`), and a test that reads a `copy` file relative to itself sees it in both runs (df-hlks).
- `.venv/bin/python scripts/testloop/cli.py <command> <module>` with `map` (branches not reached and the tests reaching each line), `mutate` (surviving mutants, mutmut; about 2 min on `dataforge/deploy/plan.py`) and `check` (deterministic pass or fail; the only judge), and `gate` (last `mutate` result against the target's `min_score`; exit 1 below it, 2 if the result is missing, partial or older than the code).
- `map`, `check` and `mutate` run the tests with an ASCII locale encoding (df-ahua.26): with `PYTHONUTF8=0`, they load the pytest plugin `scripts/testloop/plugins/testloop_ascii_locale.py`, which sets `LC_CTYPE` to `C` for the pytest session only, so `open()` without `encoding=` is ASCII there, stricter than Windows' cp1252 (which misreads such text instead of raising). Under Linux's UTF-8 locale a mutant that turns `encoding="utf-8"` into `None` or drops it read UTF-8 anyway and survived for good; now it fails on the first non-ASCII byte a test reads or writes. Only `"utf-8"` -> `"UTF-8"` (the same codec) stays equivalent. The plugin stops the run if the default is still UTF-8 (UTF-8 mode, the default from Python 3.15); on Windows the C locale gives cp1252, which also serves. `LC_ALL=C PYTHONUTF8=0` in the environment does not work: mutmut writes its mutant files (names with `ǁ`) and reads the sources with the locale's encoding, and fails. A test that reads or writes non-ASCII text must pass `encoding=` (it must for Windows anyway). The same encoding mutants are also killed by `tests-windows`, but only `mutation` counts them in a score.
- The `test-loop` skill drives these: it reads the gaps and survivors, writes properties or example tests, and runs `check`. It never decides pass or fail itself.
- Bugs it finds go to beads; a known bug is pinned with a strict `xfail` that names its issue.
- GetFinance targets (df-mbi7): `workspaces/GetFinance/scripts/report/classificacao.py` and `report_lib.py` are test loop targets. The workspace tests import them by bare name (`sys.path.insert` of `scripts/report`), so the target sets `bare_import = true` (plugin `testloop_bare_imports` loads the module under its dotted name too, or mutmut finds no mutant for the hits it records), `process_isolation = "forkserver"` (polars). The workspace's `conftest.py` loads `dataforge.testing`, the pytest plugin that also gives the engine's tests their Hypothesis profiles and the engine fixtures (df-xkhx.7), so the global `check_args` (`deterministic`) apply to these targets too. `affected.py` follows bare imports inside `workspaces/<ws>/`: a script finds its own folder and the workspace root, a test finds the root (`tests.x` is the workspace's package) and every folder under its `scripts/`; so a change to `classificacao.py` also picks `report_lib.py`. A workspace test's `conftest.py` (and what it imports, e.g. `dataforge/db.py`) is a dependency of that workspace's targets only.
- CI: job `mutation-targets` picks the targets (`scripts/testloop/affected.py`) and job `mutation` runs `mutate` for each one (or each shard of it), in parallel, and `mutation-ok` gates them. On a PR only targets whose module, tests or first-party imports (transitive) changed are picked, a target whose own table in `testloop.toml` changed is picked alone (df-n8ac.34), and all of them are picked when a shared file changed (`testloop.toml` outside its `[targets]` tables, the `scripts/testloop/` code `mutate` runs: not `affected.py`, `gate_cmd.py`, `diffcover_cmd.py`, `map_cmd.py`, `check_cmd.py`, `tests/conftest.py`, `pyproject.toml`, the `ci.yml` jobs `mutation-targets`/`mutation`/`mutation-ok` or its top-level keys other than `name`/`on`/`concurrency` (df-n8ac.40), or a non-Python or deleted file under `dataforge/` or `tests/`); push to `main` and manual runs mutate every target. A target with `shards = N` in `testloop.toml` runs as N jobs (df-n8ac.32): `mutation-targets` also publishes the matrix (`affected.py --matrix`, one item per shard), each `mutation (<module> I/N)` job runs only `cli.py mutate <module> --shard I/N` (the module's functions split by their measured mutation cost, by line count when there is no measure) and uploads its `.testloop/`, and the required `mutation-ok` downloads them all and runs `gate` per target on the N shards summed (a missing, stale or partial shard is exit 2). `mutate` warns when a run passed 240 s: raise that target's `shards`. On a PR each mutation job restores the cache of main's last run (actions/cache, key `mutmut-<module>-<I>of<N>-<hash of uv.lock and .python-version>-<run_id>`) and runs `cli.py mutate ... --cache-dir` (df-n8ac.38). A `killed` verdict is reused always; a survived, timed-out or no-test one only while every test file of the target has the bytes it had when the cache was written (df-n8ac.44: a changed or new test may kill it, so then they run again); every mutant of a function whose text changed, comments included, runs again (all of the module's when the pytest arguments or the list of test files change). A reused verdict stands through any other change outside its function: a weakened test (for a killed one), the module's constants and imports, a called function (this module or another), a base class, `copy` files, `conftest.py`, `env` in `testloop.toml`. The push run on `main`, which starts without a cache and saves it, is the audit (df-n8ac.35). The result says `"cache": "restored"` how many verdicts came from it (`cached`) and how many of those were not killed (`cached_survivors`). Locally, `--cache-dir DIR` keeps in `DIR/mutants` only mutmut's state (`mutmut-stats.json`, the `.meta` files) and each function's text hash, and only a complete run writes it. Packing (df-n8ac.39): `mutation-targets` packs the picked shards into jobs of about 200 s of estimated `mutate` (first-fit decreasing; a bigger shard runs alone; a shard with no measure counts 60 s), so a full run fits GitHub Free's 20 jobs at a time; each `mutation <n>` job runs its items one after another. The estimates are `.mutation_costs.json` (`scripts/testloop/costs.py`: each function's mutant seconds and each target's elapsed, from complete results only), which `mutation-ok` builds and caches on push and manual runs. The mutmut cache is one global entry (`mutmut-all-...`) that also holds `split-costs.json`, the costs that run split by: a PR packs and splits by that same file, so its shards match the cache it restores; the freshly measured costs only feed the next push. A malformed costs file is a warning and counts as empty. The score summary lands in the run summary and each target's `.testloop/` is uploaded. Job `testloop-tools` in the same workflow runs `tests/test_testloop.py`; the workflow also runs by hand. No LLM runs in CI; the skill stays local. When a score rises, raise `min_score` in `testloop.toml` (the gate says so, only when the four-place value it suggests is above the current `min_score`).

## Crash sweep (kill at every write)

ADR 0004 "Crash at every point". `tests/crash_sweep.py` runs a scenario in a child process and
kills it with `os._exit` (no `finally`, `except` or atexit runs) at the 1st, 2nd ... Nth write,
then lets the test check what is left on disk. A dry run counts the N write points first; each
child must die with exit code 113 at the same point the dry run saw there, or the sweep fails.
Children run in parallel (`WORKERS`); `tests/test_crash_sweep.py` tests the helper itself.

Targets today: deploy apply and rollback (`tests/test_crash_sweep_deploy.py`) and the job-run
state of `dataforge run` (`tests/test_crash_sweep_job_run.py`). About 30 s together. GetFinance's accumulating writes
(`workspaces/GetFinance/tests/test_crash_sweep_getfinance.py`, df-xkhx.2), in the workspace's suite:
`raw2cleansed.py` killed before and after each Delta commit (`polars.DataFrame.write_delta`,
`deltalake.table.TableMerger.execute`: 4 points, 8 crashes), then the next run must leave
`cleansed.transactions` as the uncrashed run did; and a rename in `edicao.db` killed before and after each
statement (7 points, 14 crashes) must leave the whole edit with the version bumped, or nothing. About 5 s.
That test loads `tests/crash_sweep.py` by path (the two `tests` packages cannot share a process) and its
child imports the scenarios as `workspaces.GetFinance.tests.getfinance_crash_scenarios`. A SQLite
write point is a method of a Python subclass of `sqlite3.Connection` (`factory=`): the C type's own
methods cannot be patched.

To add a target:

- **Scenario**: a function `f(workdir)` in a small module without pytest (`tests/<x>_crash_scenarios.py`),
  so each child starts fast. All state under the workdir (`tmp_path`); point `DATAFORGE_HOME` there
  inside the scenario when the code reads it. Keep it to 2–4 files: each write point is one child,
  and one child costs about 3 s (importing `dataforge`).
- **Write points** (`WritePoints`): the dotted names of the calls that make the target's state
  durable (`os.replace`, `pathlib.Path.write_bytes`, `sqlalchemy.orm.Session.commit`, ...). Read the
  product code to list them; a write that bypasses them is not swept. `torn` points also die
  half-way (bytes/str argument cut in half); `after` points die right after the call, which reaches
  a write the helper cannot patch (`"pkg.module.open"` patches the builtin in that module only, so
  dying after `open(path, "w")` leaves the truncated file).
- **Invariants**: check only what is promised, and cite the source next to the check (code
  docstring, `docs/`, a decision such as D16/D18 of the deploy pipeline, an existing test). A
  behaviour nobody promised is an open question for the owner (a bead labelled `suspeita`), not an
  assertion.
- **Findings**: each broken invariant becomes a bead (`bd create ... -t bug --parent <sweep bead>
  -l erro:crash`, with the step k, the state left, the mechanism and the promise) and the test
  gets `xfail(strict=True, reason="df-xxxx: ...")`, so it fails loudly (XPASS) once the bug is
  fixed and the marker must go. Test agents do not fix product code found this way.

Runs everywhere the suite runs, Windows included: plain `subprocess` with `sys.executable`, no fork.

Job-run findings (df-bw7, df-ahua.5.6), fixed: the three strict xfails now pass. `dataforge run` has 5
commits; after a crash at any of them (and a daemon start) no run or task row stays `pending` or
`running`, and each run row the crash left ends `failed` with `orphans.REASON`. The other half, a run
whose process is still alive is left alone and published as running, is
`tests/test_orphaned_runs.py` (a real `dataforge run` child held inside its task). Known gaps of this
target: the script child of a python task may outlive a killed engine (its rows are failed anyway, df-bw7.1);
rows written before owners were recorded are never reconciled (df-bw7.4); a run killed inside the daemon (API
path) is not swept, only the CLI path is (the rows and the rule are the same).

Deploy findings so far (df-ahua.5.1–5.5), all fixed: the four strict xfails now pass and the
redeploy-after-crash check is strict (no tolerated failure). Today apply has 14 write points (21
crashes) and rollback 9 (12). The ledger contract they check is in `docs/architecture.md` ("Deploy
ledger"). Still not swept: a torn log append (written through a file object; covered by
`test_a_torn_last_log_line_does_not_wedge_rollback_or_deploy` and the ledger unit tests) and power
loss (the sweep kills the process; it cannot drop unsynced writes).
